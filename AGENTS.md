# Architecture rules

Subdirectories have their own AGENTS.md (src/, supabase/functions/); read it before changing files there.

- Keep technology classification in the shared primary-IPC classifier and version the statistics cache whenever mappings change, so frontend labels and server counts stay consistent.
- Every service is named, described and grouped once in src/lib/services.ts; the shared header menu (SiteNav in PageLayout: services as direct badge links with their icons — 출원도우미 included, while 무상기술이전·식품기술이전 협의체 live at the foot of the home hero and 기술소개영상 in the home 영상 section (owner, headerBadgeServices) — the current page filled, no 더보기, 홈 left to the logo; a second header row from lg to xl, the 메뉴 panel below lg listing every service) reads from it, so pages never add their own 홈으로/service buttons or service cards (owner removed the home 서비스 바로가기 cards; the hero keeps only the 출원도우미 badge and the two hero-foot entries above; headerRight is for page-specific actions only).
- Delete server functions and UI modules once no screen calls them (verify by searching src), so unused public endpoints never stay deployed.
- Toolchain is Vite 6, Vitest 4 and React Router 7 (via react-router-dom) to stay clear of known advisories; keep tsconfig lib at ES2020-safe APIs.
- Secret-scan exceptions live in .gitleaks.toml as narrow patterns for verified public values only; keep bun.lock and package-lock.json on the same patched versions (regenerate package-lock.json with npm 11; npm 10 crashes on this tree).
- CI gates on app lint (`eslint .`; supabase/functions is excluded because the deno job checks it) and on `scripts/smoke.mjs`, which opens the vite preview build in Chromium with outside requests blocked (every route at 1280/390px, no page errors or horizontal overflow) walks public/filing-app's practice flow to the submission zip, and opens the summary from the saved responses in scripts/fixtures to require that print and PDF download are exactly two A4 pages (owner: the two-page datasheet layout must never break); update it when routes or that flow change, and re-record the fixture (keep it UTF-8, mask image tokens) when summary responses change shape.
- The service collects no personal information: no identity/contact forms and no server-side visitor records beyond aggregate counts. 기술이전 신청 links out to NATI.

## Lovable ↔ Claude co-editing
- Lovable commits straight to main; Claude works on its own branch from the latest origin/main, opens small PRs, and merges each PR into main without asking once its CI checks pass, it has no merge conflict and no unresolved review comments (owner's standing instruction); a failing check gets fixed, never skipped.
- Do not hand-edit Lovable-owned files: src/integrations/supabase/types.ts and client.ts, the committed .env, .lovable/. Schema changes go in a new supabase/migrations file (never edit an applied one).
- GitHub changes go live only after Publish (src/, public/) and a deploy request in the Lovable chat for changed functions and new migrations. `node scripts/lovable-deploy-list.mjs <base> [head]` lists them (a function counts as changed when its files or any imported _shared module changed); CI writes the same list ("Lovable 배포 목록") and every PR body states it or says Publish alone is enough.
- Supabase and the KOSIS API are connected through Lovable (owner, 2026-11): secrets such as KOSIS_SERVICE_KEY and LOVABLE_API_KEY live in Lovable's Supabase settings, so never ask for, add or commit keys. A market labelled (AI 추정치) means summarize-patent/kosis.ts has no series whose scope matches it (global markets never do), not a missing key; add a series only after checking the KOSIS table's years and that its category covers the whole market. The data.go.kr key allows about 10 requests per second, so call KOSIS one table at a time.
- Prefer changes that need no function deploy: copy, layout, public/filing-app and admin-stored site settings ship without one.
- Consortium list requests use a monotonically increasing request ID, invalidated on selection change and unmount, so stale success, error and pagination responses cannot affect another organization's list.
- Daily security checks run in a dedicated GitHub Actions workflow with separate secret and lockfile dependency scans, so neither a scan failure nor unrelated app CI prevents the other scan from running; this does not schedule Lovable's managed deep or database scans.
